## 0. 结论摘要

**总评：这是一份明显高于同类脚手架平均水准的工程。** 分层清晰、护栏密集、“默认安全 / fail-closed”原则几乎贯穿每一条 I/O 路径，注释解释的是**为什么**而不是**做了什么**（很多条目还附了真实踩坑记录）。对官方 Pi SDK 的能力也已按“能走官方就走官方、官方更弱则有意保留自定义”的原则逐项对齐（详见 [`能力与边界.md`](能力与边界.md)）。

**当前 HEAD 门禁全绿**（实测）：typecheck 0 错 · lint:unused 0 · test **376 用例 / 0 失败** · test:web **11/11** · smoke **23/23** · build 产出 `dist/` · verify:embed **8/8** · e2e **39/0跳/0失败**。

仍存在的已知改进项（按优先级，均未阻断）：

| 优先级 | 问题 | 证据 |
|---|---|---|
| **P1** | 文件服务把 cwd 下的 `.env` 经 HTTP 原样吐出 | `server.ts` 默认 root=`process.cwd()` + `file-routes.ts` |
| **P1** | `PI_API_KEY` 进入 `process.env`，被所有 `exec` / MCP 子进程继承 | `config.ts` `loadEnvFile` + `exec/runner.ts` env |
| **P1** | `bash` 开启后仅靠正则可绕过，无路径约束 | `extensions/guard.ts` |
| **P2** | `db.query()` 全量载入再截断，行数上限形同虚设 | `db/index.ts` |
| **P2** | 快照构建每周期 O(n) 至少三遍 | `session-hub.ts` `buildState` |
| **P3** | `session-hub.ts` 体量过大（三合一）+ 大量 SDK 私有形状断言 | 全文 |

> 这些是安全/性能/可维护性的优化建议，不是当前缺陷；项目定位已将其中部分（如 “guard 不是沙箱”）作为声明过的取舍。是否推进由业务决定。

## 1. 项目定位与整体结构

### 1.1 定位
不是"又一个编码助手壳"，而是**垂直 Agent 的起跑线**：clone 下来能跑，业务通过接口注入（`buildAgent()` / `createApp()`），不需要改 `node_modules/@earendil-works`。

### 1.2 目录组织（`src/` 90 个 `.ts` 文件：56 非测试 + 34 测试，按职责分层）

```
src/
├── 入口层      index.ts(CLI) server.ts(Web) lib.ts(库) setup.ts(写 ~/.pi/agent)
├── 组装层      agent.ts ★ 零件→session    app.ts ★ HTTP   config.ts / cli-args.ts
├── 编排层      session-hub.ts ★(1530行)  snapshot.ts  protocol.ts(协议单源)
├── 传输层      sse.ts  transport/ws.ts
├── 会话树      sessions/{store,edit}.ts
├── 能力层      tools/{index,registry,exec,knowledge,database,current-time}.ts
│              skills/  knowledge/  prompt-templates/  prompts/composer.ts
├── 策略层      approval/{rules,policy,gate,watchdog}.ts  modes/plan-mode.ts
├── 集成层      mcp/{client,bridge}.ts  subagents/index.ts  exec/runner.ts
├── 基础设施    log.ts  metrics.ts  settings.ts  provider-keys.ts  graceful.ts
│              files/service.ts  context/budget.ts  http/*（加固/错误/限流/路由）
└── 测试        42 个 *.test.ts（376 用例）+ 前端 11 用例
```

**优点**：`protocol.ts` 作为协议单源 + 编译期完备性断言（`satisfies` + `Exclude extends never`），新增命令漏登记会编译失败，这个手法很干净。`http/` 把路由、错误、加固、限流拆开，`app.ts` 只剩装配。

**问题**：`session-hub.ts` 是唯一的结构性肿瘤（见 §6.3）。

## 3. 核心模块与主要功能

| 模块 | 职责 | 实现要点 |
|---|---|---|
| `agent.ts` | 组装：模型 + 提示词 + 工具 + 扩展 → session | `resolveToolList()` 刻意在 `createSession` **内部**求值，因为 SDK 的 `tools` 会变成构造后不可改的硬白名单（MCP 工具只能"下次建会话生效"）。`model` 改成 getter 消除"切模型后 `/info` 说谎"的一类 bug。 |
| `session-hub.ts` | `SessionHub → ClientSession → Conversation` | 快照驱动、多对话（cap 8 + LRU）、审批态、计划模式、压缩、会话树编辑。 |

| `transport/ws.ts` | 双向 WS | Origin/Host 同权威校验、背压丢快照 + 慢客户端终止、`serializeShared` WeakMap 缓存、pending 队列回放。 |
| `approval/*` | 规则引擎 + 三档策略 + HITL 闸门 + 看门狗 | **`deny` 不可被策略覆盖**（真安全属性）；超时判拒；`modify` 原地改 `event.input`。 |
| `exec/runner.ts` | 进程执行（非 PTY） | 进程树 kill、realpath 双重校验、输出/任务数/寿命全封顶。 |

| `mcp/{client,bridge}.ts` | 自研 MCP stdio 客户端 + 桥 | 行缓冲、请求超时、spawn 失败单独通道、改配置即生效。 |

## 4. 关键代码逻辑与数据流向

### 4.1 `POST /chat`（REST + SSE）
```
HTTP body → 校验 message（必须在写 SSE 头之前，否则改不了状态码）
  → busy 守卫 → 写 200 + SSE 头
  → session.subscribe(translateEvent → res.write)
  → session.prompt(message)
  → 失败：toAppError → 只暴露白名单 code 的 message，其余走通用文案 + 服务端日志
  → finally: done 帧 + res.end + busy=false
```
`res.on("close")` 而非 `req.on("close")` —— 注释指出 `req` 的 close 在 body 读完就触发，会误杀刚起步的一轮。这类细节处理得很到位。

### 4.2 `POST /chat`（WS，产品化路径）
```
hello → ready（必须首帧）→ hub.attach → applyToolSet(registry.enabledNames())
      → setThinking(settings.thinkingLevel) → flushPending(回放握手期命令)
prompt → ClientSession.prompt → Conversation.prompt → SDK session.prompt
SDK 事件 → Conversation.onEvent（翻译 + 快照调度 + 看门狗 arm/disarm）
       → 边界事件(agent_end/turn_end/tool_execution_end/message_end/compaction_end)立即 flushSnapshot
       → 其余 scheduleSnapshot（节流）
       → SnapshotEmitter 判增量/全量 → push → ClientConn.send（背压丢弃 + 续传）
```

### 4.3 工具调用闸门（三层叠加，顺序即优先级）
```
SDK tool_call
 ├─ guard 扩展        ：正则危险命令 + 路径越界 → { block }
 ├─ planMode 扩展     ：写类工具/能力 → { block }（硬闸门）+ 提示词软约束
 ├─ approval 扩展     ：规则引擎 → deny(不可覆盖) / ask(问人，超时判拒) / allow
 └─ 执行 → tool_result → audit 扩展（耗时日志）
```
注意：`guard` 与 `approval` **各自维护一份危险命令正则表**（`DANGEROUS_BASH_RULES` vs `BUILTIN_RULES`），已出现内容漂移（`git reset --hard` / `chmod -R` 只在 approval 里有，guard 里没有）。

### 4.4 会话恢复（重启后接回）
```
客户端只提交 conversationId（绝不传路径）
 → SessionCatalog.get(id) 查索引拿 sessionFile
 → assertSessionFileAllowed（绝对路径 + .jsonl + realpath 在允许根内，根 realpath 失败即弃）
 → SessionManager.open(path)
```
`assertSessionFileAllowed` 在 `newConversation` 与 `resolveSessionManager` 各查一次 —— 双重校验，不依赖调用方注释。设计正确。

### P1 — 安全

#### P1-1 文件服务把 cwd 下的 `.env` 直接吐给任何能连到端口的人
`server.ts:302`：
```ts
files: new FileService({ root: process.cwd() }),
```
`.env` 就在 `process.cwd()`，而 `FileService` 只做路径越界校验、**没有敏感文件名黑名单**：
```
GET /files/read?path=.env      → 文本预览
GET /files/raw?path=.env       → 流式原文（无 Range 且 < 512KB 时整份返回）
```
这与项目自己在 `provider-keys.ts` 反复强调的"原始 key 及其任何派生形式永不出服务端"直接冲突 —— provider-keys 守住了，`.env` 这条旁路没守。
**缓解**：默认只绑 loopback 且无鉴权，实际暴露面有限；但一旦 `PI_HOST` 改成非 loopback（README 允许这么做，仅打警告），就是明文泄露。
**修复**：
1. `FileService` 增加 `denyNames`（默认含 `.env`、`.env.*`、`*.pem`、`*.key`、`id_rsa`、`auth.json`、`credentials*`），在 `resolvePath` 后按 basename 拦；
2. `/files/raw` 与 `/files/read` 复用同一黑名单；
3. 或把文件服务 root 从 `process.cwd()` 收到一个显式子目录（如 `workspace/`）。

#### P1-2 `PI_API_KEY` 进入 `process.env`，被所有子进程继承
`config.ts:158-167`：
```ts
process.loadEnvFile?.(envPath);   // 把整个 .env 灌进 process.env，含 PI_API_KEY
```
`exec/runner.ts:425,433` 与 `mcp/client.ts:71` 都是 `env: process.env`（MCP 是 `{...process.env, ...options.env}`）。于是开启 `coding` 后，任何 `bash`/`exec` 命令、任何 MCP 子进程都能：
```bash
echo $PI_API_KEY
```
README 说 "`PI_API_KEY` in `.env` is only consumed by setup and never sits in the request path" —— 对"发往模型的请求"成立，但**对进程环境不成立**。
**修复**：
1. `loadEnvFile` 只挑需要的变量（`PI_MODELS/PI_MODEL/PI_PROVIDER/PI_HOST/...`）注入，或注入到一个独立的 config 对象而不是 `process.env`；
2. 子进程 env 做白名单裁剪，剔除 `PI_API_KEY*`；
3. 文档改为准确表述（"密钥在 setup 后写入 `~/.pi/agent/auth.json`(0600)，运行期不再需要 `.env`"）。

#### P1-3 `bash` 开启后无路径约束，正则可被常规手段绕过
`extensions/guard.ts:115-119`：
```ts
const shellHit = dangerousShellCommand(...);   // 正则表
if (shellHit) return block(...);
if (isToolCallEventType("bash", event)) return undefined;   // ← 之后完全放行
```
`bash` 不经过 `isPathInsideCwd`，命令体内可 `cd /`、`cat /etc/passwd`、`curl` 外网。而正则表本身可被绕过：`find . -delete`、`truncate -s0 f`、`> f`、`python -c "..."`、`node -e`、`base64 -d | sh`、`$'\x72\x6d'` 等都不在表内。同时 `isPathInsideCwd`（`guard.ts:89-94`）**不解析符号链接**，read/write/edit 可经 symlink 逃逸 —— 而 `FileService` 与 `exec` 都做了 realpath 校验，**三层保护强度不一致**。
**这是项目自己声明过的取舍**（"这不是沙箱"），但 README 的 "Hardened by default" 表述容易让人误判强度。
**修复**：
1. 文档层面把 "hardened" 降级为 "有基础拦截，非沙箱"，并在 `coding` 档显著提示；
2. 代码层面把 `guard` 的路径校验换成 realpath 版（可直接复用 `FileService` 的 `assertRealpathInside` 思路），至少让 read/write/edit 与文件服务同一强度；
3. 把两份危险命令表**合并成单一事实源**（例如 `approval/rules.ts` 的 `BUILTIN_RULES` 为源，`guard` 从中派生），消除漂移。

#### P1-4 审批默认关闭 → `ask` 类规则默认不生效
`settings.ts:264-265`：`toolApprovalEnabled: false` + `approvalMode: "off"`。叠加 `PI_BUILTIN_TOOLS=off` 默认，整体风险可控；但要清楚：**默认状态下只有 `deny` 类规则（mkfs/dd/fork-bomb/shutdown）和 guard 的正则拦截在起作用**，`rm -rf` 这类 `ask` 规则是静默放行的（靠 guard 兜住）。接入生产时应显式打开审批。

### P2 — 性能

#### P2-1 `db.query()` 全量载入再截断
`db/index.ts:328-331`：
```ts
const stmt = db.prepare(sql);
const raw = stmt.all(...params) as ...;          // ← 先把整张表拉进内存
const truncated = raw.length > maxRows;
const rows = (truncated ? raw.slice(0, maxRows) : raw).map(...);   // 再截断
```
上方注释写"`SELECT * FROM huge_table` would otherwise pull the whole table into memory" —— **实现恰好没做到**。行数上限只限制了"返回给调用方多少行"，没有限制"载入多少行"。
**修复**：改用 `stmt.iterate()` 边取边判，取满 `maxRows + 1` 即停；或对无 `LIMIT` 的语句自动包一层 `SELECT * FROM (<sql>) LIMIT ?`。同时保留 `totalRows` 语义（可只报告"≥maxRows"）。

#### P2-2 快照构建每周期 O(n) 至少三遍
`session-hub.ts:565-616` `buildState()` 一次调用里：
- `currentMessages()` → 遍历**全部**消息做投影（`MAX_SNAPSHOT_MESSAGES` 只砍传输体积，投影照做）；
- `entryIds()` → `manager.buildContextEntries()` **走一遍完整会话树**建 Map；
- `estimateTokensCached()` → O(n) 累加；
- `planTrim()`（`:609` `overBudget: this.planTrim().trimmed`）→ `planContextTrim` + `estimateConversationTokens`，**又是两遍 O(n)**。

节流 60ms 意味着流式输出时每 60ms 就有一次 ~5n 的工作量。`snapshot.ts:77-84` 的增量判定同样是 `for i < prev.length` 的 O(n) 比较。
**修复**：
1. `entryIds()` 结果按 `manager` 版本号缓存，仅在 `entry_appended` / 树变更时失效；
2. `planTrim()` 的 `overBudget` 改成"估算 token > softCap"的廉价判断，不要每周期跑完整裁剪计划；
3. `estimateTokensCached` 维护增量总和而不是每次重算；
4. 增量判定改为记录 `emittedLength` 而非逐元素比较（投影引用稳定，长度不变即前缀未变）。

#### P2-3 其他
- `subagents/index.ts` 的 `waiters` 等待队列**无上限**（只封了并发数 3）。模型一轮内连派几十个会堆一串 Promise。
- `metrics.ts:114` `METRICS[name].name` 对未知名字会抛，注释却写"unknown metric names … are ignored in production paths" —— 实际靠调用方自觉。

### P3 — 可维护性

#### P3-1 `session-hub.ts` 体量偏大（~1530 行）且三合一
`Conversation` 一个类里混了：事件翻译、快照构建、标题推导、会话树操作、压缩、计划模式、审批态、生命周期。`ClientSession` + `SessionHub` 又各占一段。这是全项目唯一读起来吃力的文件。
**建议拆**：`conversation/events.ts`（onEvent 翻译）、`conversation/state.ts`（buildState + 投影缓存 + token 缓存）、`conversation/tree.ts`（rename/rollback/edit/fork 转发）、`conversation/index.ts`（编排 + 生命周期）。纯函数与副作用分离后，快照那块还能单独基准测试。

#### P3-2 大量对 SDK 私有形状的鸭子类型断言
```ts
(session as { compact?: (i?: string) => Promise<unknown> }).compact        // :712
(this.session as { agent?: { state?: { messages } } }).agent.state         // :529
(this.session as { sessionManager?: SessionManager }).sessionManager        // :516
(session as Session & { setSessionName?: (n: string) => void })            // :814
```
SDK 锁死 0.83.0，升级时这些点会静默变成 `undefined`（部分有 `typeof === "function"` 兜底，部分没有），失败方式可能是"功能静默失效"而不是报错。
**建议**：集中到一个 `sdk-adapter.ts`，把每处私有访问收敛成带类型 + 存在性检查 + 缺失时明确降级的函数。至少做到"一处升级、一处改"。

#### P3-3 双通道逻辑重复
`app.ts`（REST）与 `transport/ws.ts` 各自实现 `set_model`、`compact`、能力目录构建、模型列表整形。协议单源只统一了**类型**，没统一**行为**。建议把"能力目录构建""模型列表整形"抽成共享函数（`buildCapabilities` 已在 ws.ts，REST 的 `/capabilities` 是另一份手写）。

#### P3-4 注释与实现漂移

### P4 — 小问题
- `/files/upload`（`http/file-routes.ts:181`）：base64 解码成 Buffer 后写 `buf.toString("utf8")` → **二进制上传必然损坏**（非 UTF-8 字节变 U+FFFD），且 `write()` 本身又拒绝二进制扩展名。要么改走二进制写入路径，要么明确只支持文本并校验。
- `session-hub.ts:580` `buildState()` 里写 `rev: 0`，随后被 `SnapshotEmitter` 用自增 rev 覆盖 —— 该字段是死的，容易误导。
- `loadEnvFile`（`config.ts:162-166`）吞掉所有异常，`.env` 里一个笔误会让密钥静默缺失。
- `isClientMessage`（`protocol.ts:349-355`）只检查 `type` 是字符串，任何带字符串 `type` 的对象都会进 dispatch；各命令的字段校验散落在 switch 里，风格不统一。

## 6. 做得好的地方（应当保持）

1. **fail-closed 一致性**：`assertSessionFileAllowed` 在任何 `SessionManager.open` 之前；`FileService` realpath 失败即拒；`sanitizeIndexEntries` 双向过滤；根目录 realpath 失败就丢掉这个根而不是退回字面路径。
2. **密钥纪律**：`provider-keys.ts` 的 `describe()` 在**类型层面**就不可能返回 `apiKey`；落盘 0600；临时文件也 chmod。这是教科书式的做法（唯一漏网的是 `.env`，见 P1-1/P1-2）。
3. **`deny` 不可被策略覆盖**（`approval/policy.ts:100-108`）—— 真正的安全属性，比"照抄 pi-web-ui"更进一步。
4. **资源封顶**成体系：`MAX_JOBS/MAX_FINISHED/MAX_OUTPUT_BYTES/MAX_COMMAND_CHARS/MAX_SNAPSHOT_MESSAGES/MAX_INDEX_ENTRIES/MAX_USER_RULES/MAX_MCP_SERVERS/MAX_DOCS` + 背压丢快照 + 慢客户端终止 + 工具看门狗 + 审批超时判拒。
5. **原子写 + 损坏回落**在 settings / rules / provider-keys / index / plan-mode 五处统一（tmp + rename + 失败告警不回滚内存）。
6. **错误分层**：`AppError.safeToExpose` 默认 false，`internal` 的真实文案只进日志；`/chat` 因为状态码已提交，**在 SSE 内用同一套规则**翻译错误 —— 这个坑踩得很清楚。
7. **优雅停机的兜底定时器先建后跑步骤**（`graceful.ts:58-71`），并注释记录了原实现"进程永久挂死"的真 bug。
8. **日志自动脱敏**（`log.ts`）+ 深度受限递归 + Error 特殊处理（否则 spread 会丢 message）。
9. **测试策略**：用契约忠实的 session 替身驱动真实编排栈，无需网络与 API Key 就能覆盖 wiring 回归。
10. **MCP `onError` 永远挂载**（`mcp/client.ts:83-85`）—— 因为 ChildProcess 的未处理 `error` 会直接带走进程，这个细节很少人做对。
