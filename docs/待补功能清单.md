# pi-starter 后端功能缺口清单

> 性质：**待补必做清单**，不是规划建议。每项给出「缺什么 / 为什么必须 / 验收标准」。
> 判定基准：`pi-web-ui@0.99.0` 的通用能力（与业务无关的那部分）。
> 基线：`f3cd71f`。
>
> 定位前提：pi-starter 是**脚手架**。判据是「与业务有无关系」，不是「我做过没有」——
> 文件、终端、模型管理、运行模式、扩展能力都是任何 Agent 应用的基本需求，不是业务层。

我的 10 项独有里7 项是工程纪律（脱敏日志 / 类型化错误 / 指标 / 门禁 / 集成测试 / 上限护栏），
只有 SQLite 工具与知识库算真功能。**功能数量上他碾压，这是不粉饰的事实。**

## 第一阶段 · 统一治理（地基，必须最先做）

> 这一层不是「功能」，是**脚手架的地基**。不先做，后面每加一个功能，业务方接入都会掉进洞里。

### G1. WS 命令注册表

- **缺什么**：`ws.ts:205` 是 `private dispatch` + 封闭 `switch (msg.type)`，零扩展点。业务方无法注册任何命令。
- **症状**：业务方发 `{type:"my_cmd"}` → 落入 `default` → **静默无响应**，前端永远等不到回音，也无任何报错。
- **后果**：想加自己的 WS 命令必须改 `protocol.ts` + `ws.ts` **两个内核文件**，直接破坏「业务逻辑经接口注入」的立项目标。
- **要做什么**：提供 `registerCommands({ my_cmd: { handler, describe } })` 注册入口，内核 dispatch 改为查表；**未注册命令必须返回明确 error 帧**，不得静默。
- **验收**：业务方注册自定义命令 → 前端调用成功；调用未注册命令 → 收到明确错误帧而非静默；内置 19 个命令行为不变。

### G2. HTTP 路由注入钩子（消除内部细节泄漏）

- **缺什么**：`registerErrorHandler(app)` 在 `createApp` **内部**挂载（第 270 行），业务方拿到 `app` 后加的路由排在它**之后**，永远走不到错误处理器。
- **实测症状**：业务方 `throw notFound("没有这个东西")` → **500 + HTML 堆栈页**（而非 404 + JSON）；`throw new AppError("internal", "数据库密码是 hunter2，路径 D:\\secret\\db.sqlite")` → **密码、路径、源码行号全部原样返回客户端**。
- **关键影响**：脚手架提供的「internal 默认隐藏」保护**对业务方完全失效**。这是静默陷阱——内核自己受益，业务方受害。
- **要做什么**：`createApp` 接受 `configure?: (app) => void`，在错误处理器**之前**注入业务路由。
- **验收**：业务方在 `configure` 里挂的路由抛 `AppError` → 被统一处理；`internal` 返回通用文案且**响应体不含**原始 message/路径/堆栈。

### G3. 协议可扩展

- **缺什么**：`ClientMessage` / `ServerMessage` 是封闭判别联合，业务方无法注册自己的消息类型（类型层面就进不去）。
- **要做什么**：让业务方命令有类型通路（泛型注册 + 类型推导），不改内核即可获得类型检查。
- **验收**：业务方注册的命令在编辑器里有补全和类型检查。

### G4. 统一生命周期回收

- **缺什么**：业务方注册的工具/命令/资源无法被 `dispose()` / 优雅停机回收。
- **要做什么**：注册时返回 disposer，停机统一回收。
- **验收**：停机后无残留定时器、无泄漏。

## 第二阶段 · 内核自身完整性

> 与业务无关，是内核自己的漏洞。业务方写前端时会立刻撞上。

### G5. `agent_end` 无 `run_end` 信号

- **缺什么**：快照策略里判断了 `agent_end` 会立即 flush（`session-hub.ts:267`），但**没有对应 `case` 分支**，不发 `run_end`。
- **后果**：前端拿不到「本轮完成」，也拿不到 `stopReason`，只能靠快照里 `isStreaming` 轮询推断。
- **参照**：pi-web-ui 以 `agent_end` 为汇聚点（发`run_end` + 刷会话列表 + 刷标题 + 触发钩子）。
- **验收**：`run_end` 进入协议单源；一轮结束时前端收到 `run_end` 且带 `stopReason`。

### G6. `tool_execution_update` 未处理

- **缺什么**：9 类SDK 事件里没有它 → 无 `tool_delta` 消息。
- **后果**：工具的流式中间输出完全丢失，**长工具运行期间界面「无反应」**。
- **验收**：工具流式输出经 `tool_delta` 到达前端。

### G7. `capabilities.commands` 的扩展点 ✅ 已完成（`c8e20cb`）

- **此前判断有误**：曾写成「死字段 / 永远空数组」。实际它有来源——`DEFAULT_COMMANDS`
  硬编码 4 条（`/new` `/model` `/abort` `/state`）。准确说法是「**硬编码 + 无扩展点**」。
- **已做**：`WsRuntime.slashCommands` 让嵌入方追加自己的斜杠命令，进入能力目录。
- **仍存在**：内置那 4 条仍是硬编码常量，不随能力变化自动推导。若要更彻底，应从
  已注册命令与工具反推。这是**可选改进**，不是缺口。

### G8. 缺 `turn_start/turn_end`、`entry_appended` ⚠️部分完成

- **`entry_appended` 已处理**（`c8e20cb`）：该分支用于刷新会话标题。
  但它**没有**变成给前端的消息，协议里没有对应帧——它与 `run_end`/`tool_delta`
  不是一类东西，不要混为一谈。
- **仍缺**：`turn_start` / `turn_end` 未处理，运行轨迹粒度仍粗。
- **验收**：轨迹事件完整，进入协议单源。

## 第三阶段 · 文件与执行环境

> **最基本的能力**：Agent 不读写文件、不执行命令，等于没有手。这些与业务无关。

### G9. 文件服务

- **参照**：`files-service.ts` 1535 行 + `text-sniff.ts` + `file-archives.ts`
- **要做什么**：文件 CRUD（list / read / write / create / rename / delete / copy）· 目录浏览 · 预览（只读前 512KB + 文本/二进制嗅探）· 上传下载 · 媒体走Range 请求 · 路径越界防护
- **安全底线**（必须与pi-web-ui 持平）：路径穿越拒绝、符号链接处理、二进制不硬塞进上下文
- **验收**：越界路径被拒；预览不一次读全文件；大文件走Range。

### G10. 命令执行增强

- **现状**：有 SDK 内置 `bash`。
- **要做什么**：后台任务跟踪（Agent 启动的监听进程可被识别与停止）。
- **参照**：`bg-servers.ts` 400 行（bash 前后拍监听快照 diff + 父链回溯过滤 + 闲置清理）。
- **⚠️ 完整 PTY 终端（`terminals.ts` 2330 行）暂缓**：目标项目在 Windows ConPTY 自愈、MSYS2 全局控制台 128 上限泄漏死锁上耗掉了整个文件。脚手架阶段用 `child_process` 级执行足够，PTY 留到业务真需要交互式终端时再做。

## 第四阶段 · 模型管理

> 模型是 Agent 的动力源。现在只有一个切换开关，不够用。

### G11. 多 API 密钥

- **参照**：`provider-keys.json` 的 `{provider:{activeKeyName, keys:[{name,apiKey}]}}`

### G12. 模型配置增删改查

- **验收**：完整走通授权；任何响应不含令牌。

## 第七阶段 · 持久化

### G19. 配置与规则落盘 ✅ 已完成（`bd40464`）

- **已做**：`fileSettingsPort()`（原子写 + 损坏回落）、`loadApprovalRulesFromFile()` /
  `saveApprovalRulesToFile()`、`server.ts` 接入 + 停机写回规则。
- **复核后补强**（见下方复核轮 R2/R3）：配置文件的**非法字段**不再让服务起不来；
  审批规则的 `match.value` 现在被校验。

### G19b. 规则编辑 API ❗仍未实现（复核发现的新缺口）

- **现状**：规则**能读能落盘**，但**没有任何编辑入口**——全仓库 `upsert` / `setUserRules`
  只在测试里被调用，没有 HTTP 路由、没有 WS 命令。
- **后果**：落盘只补上了「启动时读」，「运行中改」整条链路不存在。规则目前只能手改
  JSON 文件。而规则只在**优雅停机时**写回，所以进程崩溃或被强杀时，任何手改都会丢。
- **要做什么**：`GET/POST/PUT/DELETE /approval/rules`（或等价 WS 命令）+ 变更即落盘。
- **验收**：通过 API 改规则 → 立即生效 → 重启后仍在。
- **注**：设置的 `patch()` 是**每次都写盘**的，与规则不同——不要把两者混为一谈。

### G20. 会话持久化

- **现状**：`SessionManager` SDK 已支持落盘（CLI 模式在用），Web 侧未接。
- **要做什么**：Web 侧会话持久化 · 重启可恢复对话。
- **验收**：重启后对话列表与内容可恢复。

## 顺序原则

```
治理 → 手（文件/执行）→ 脑（模型）→ 行为控制（模式/子代理）
     → 扩展（MCP）→ 记忆（持久化）→ 生态（插件）
```

**治理排第一的理由**：没有它，后面每个功能交付给业务方时都会掉进「异常泄漏 + 无法扩展」两个洞里，
等于每个功能都要返工一遍。

## 明确不做（脚手架的边界）

多用户 / 支付 / UI 框架 / 完整 PTY 终端 / Electron 桌面端 / 定时任务调度 —— 这些是产品层需求，
不是脚手架地基。真需要时以插件或示例形式接入，不进内核。

### 扩展点的真实形态（别再当函数讲）

```ts
const ws = attachWebSocket(server, {
  agent, hub, cfg, registry, settings,
  commands: {                          // ← 扩展点是「传给 attachWebSocket」，不是调用某个注册函数
    biz_sum: defineCommand<{ a: number; b: number }>({
      describe: "求和",                 // 仅用于能力目录展示
      handler: ({ payload, send, session, runtime }) => { /* ... */ },
    }),
  },
  slashCommands: [{ name: "/biz", description: "..." }],
});
```

- `defineCommand<P>()` **只在编译期给 `payload` 标注类型**，运行时**不做任何校验**——
  畸形 payload 会原样进handler，需要业务方自己校验。
- 未注册命令返回的错误帧里，`registered:` 列出的是**已注册的自定义命令**，不是内置命令全集。
- 内置命令不可被同名注册覆盖（内置类型由 `CLIENT_MESSAGE_TYPES` 判定）。

### 两条通用教训

1. **安全校验必须 fail-closed**。「字面路径在 root 内」不等于「真实路径在 root 内」——
   符号链接正是把两者分开的机制，而 realpath 失败恰好是这道检查失效的时刻。
   证明不了安全就拒绝，服务不可用比放行一个文件更可接受。
2. **「文件坏了能回落」要分两层测**：解析失败是一层，**解析成功但内容非法**是另一层。
   只测前者会漏掉「一个多余字段让服务起不来」这类更隐蔽的故障。

## 每步的完成门禁

任何一项完成后，以下必须全绿：

```powershell
npm run verify        # typecheck + test + smoke + build
npm run lint:unused   # 零未使用符号
```

新增功能必须带测试；接线类修复必须做**反向验证**（改回缺陷形态确认测试变红）。
