# pi-starter × pi-web-ui 后端功能边界对比

> 目的：为「丰富后端功能」确定下一步方向。
> 基线：`pi-starter` @ `f3cd71f`（2026-10-08）vs `pi-web-ui@0.99.0`。
> 方法：**以当前代码实测盘点**，不采信任何既有结论。
>
> ⚠️ `pi-web-ui后端功能全景分析.md` §5 的差距矩阵写于本轮两轮加固**之前**，其中
> 「单 session/并发 429」「SSE 单向逐条」「无快照驱动」「无看门狗」「无规则引擎」
> 等判断**已全部过时**，该矩阵不可直接用作决策依据。

---

## 一、结论先行

**骨架已经对齐，差的是业务面。**

两轮加固把 pi-starter 从「SSE 单向事件流」推到了与 pi-web-ui **同构的骨架**：
快照驱动、协议单源、多对话并发、工具注册表、看门狗、审批规则引擎、上下文预算、
提示词组合、传输层安全 —— 这九项**不再是缺口**。

剩余差距集中在**业务子系统**（文件/git/终端/插件/多密钥/模式），是量级差距而非结构差距。
其中约 **6 项属于骨架的完整性问题**（成本低、价值高），其余是产品化工程量。

规模对比：pi-starter **56 文件 / ~9.9k 行** vs pi-web-ui **server/ 130 文件**（`agent-service.ts` 单文件 15398 行）。

## 二、pi-starter 已对齐的部分（不再是缺口）

| 能力域 | pi-starter 现状 | 与 pi-web-ui 关系 |
|---|---|---|
| 快照驱动 | `snapshot.ts` + `UiState` 单源 + `rev` 链 + 增量 delta + 背压丢弃 + 断链自愈 | **对等** |
| 协议单源 | `protocol.ts` 判别联合 + `CLIENT_MESSAGE_TYPES` **编译期完备性断言** + 版本协商 | **更强**（pi-web-ui 靠 `check:protocol` 脚本，pi-starter 是编译不过） |
| 多对话并发 | `SessionHub → ClientSession → Conversation`，每对话独立 session，上限 8 + LRU | **对等**（缺项目维度与过户） |
| 工具注册表 | 数据驱动 `ToolSpec`（capabilities/risk 元数据）+ ActiveSet 运行中开关 | **更强**（见下节） |
| 工具看门狗 | `approval/watchdog.ts`，超时 abort、不 unref、豁免问人类的工具 | **对等** |
| 审批规则引擎 | 10 条内置高危规则 + 三档策略 + HITL + `modify` 改参放行 | **对等**（匹配器种类略少） |
| 上下文预算 | token 估算 + 软上限 + 裁剪计划 + 使用率 | **对等**（缺主动压缩工具） |
| 提示词组合 | 7 层 token 模板 + 未知 token 校验 | 同构（pi-web-ui 11 层） |
| 传输层安全 | Origin/Host 同权威校验 + loopback + body 上限 + 5 个安全头 + 限流 + 只读 SQL 校验 | **部分超越**（见下节） |

## 三、pi-starter 明确更好的地方（不要盲目照搬）

| # | 维度 | pi-starter | pi-web-ui | 原因 |
|---|---|---|---|---|
| 1 | 工具注册 | 数据驱动元数据表，新增工具登记一次 | `AGENT_TOOL_CATALOG` 硬编码常量 + `installToolOverrides` 覆盖链 | 目标项目历史包袱更重 |
| 2 | 工具注入方式 | 走 SDK 公开 API | 直接改 `session._customTools` **私有字段** | 私有字段随 SDK 升级即碎 |
| 3 | 模型切换 | `hub.setModel()` 单一真源，REST/WS 强制同源 | 需 `rememberProjectModel` 兜底「新对话切走会丢」 | 目标项目存在状态分裂隐患 |
| 4 | 慢客户端 | 连续丢弃超阈值 `terminate()` | 只丢快照，不断连 | 僵尸连接会持续占内存 |
| 5 | 错误处理 | `AppError` 类型化，`internal` 默认隐藏内部细节 | 各路由自行处理 | 避免路径/SQL/SDK 细节外泄 |
| 6 | 可观测性 | `/metrics` 14 项指标 + 结构化脱敏日志 | 无对等物 | — |
| 7 | SQL 防护 | 只读校验器（全文 token 扫描，CTE 内写入一并拦截） | 无 SQL 工具 | — |
| 8 | 知识库 | 检索 + 全文 + 体积上限（读取前拦） | 无对等物（只有附件） | — |
| 9 | 测试分层 | 集成测试用 SDK 契约替身驱动真实编排栈，**CI 可跑** | — | — |

**结论：不应把目标项目当作「更全因而更优」的模板整体照搬。** 上述 9 处照搬反而是退步。

## 四、缺口清单（按「成本 × 价值」排序）

### 🟠 第一梯队：骨架完整性（成本低、价值高，建议优先）

| # | 缺口 | 现状 | 影响 | 参照体量 |
|---|---|---|---|---|
| G1 | **`agent_end` 无 `run_end` 信号** | 快照策略里判断了 `agent_end` 会立即 flush，但**没有对应 case 分支**，前端只能靠快照里的 `isStreaming` 推断轮次结束 | 前端拿不到「本轮完成」与 `stopReason`，运行轨迹缺失 | pi-web-ui 以此为汇聚点（发 `run_end`+刷列表+标题+钩子） |
| G2 | **`tool_execution_update` 未处理** | 9 类事件里没有它 → 无 `tool_delta` | 工具的流式中间输出完全丢失，长工具运行期间界面「无反应」 | 一个 case 分支 |
| G3 | **`capabilities.commands` 是死字段** | `protocol.ts` 定义了，全项目**无任何处填充** → 永远空数组 | 又一处「声明≠生效」；前端按此渲染斜杠命令菜单将恒为空 | 需实现或删除 |
| G4 | 缺 `turn_start/end`、`entry_appended` | 未处理 | 轨迹粒度粗、会话列表不刷新 | 三个分支 |

## 五、差异产生的原因（理解这点才能定对方向）

1. **定位不同**：pi-web-ui 是长期演进的生产级驾驶舱（130 文件、单文件 1.5 万行），有历史沉淀也有历史包袱；pi-starter 是**起步模板**，要求「业务逻辑经接口注入」，明确不做 UI/多用户/支付。
2. **pi-web-ui 的能力分布不均**：能力最密集的是插件系统（4712 行）与 DSH 第二引擎（4941 行），而会话持久化、SQL 防护、知识库这类基础面反而没有投入。**照搬会继承其失衡**。
3. **pi-starter 的短板在"接线完整性"而非"功能数量"**：两轮修复的 9 项里有 7 项属于「声明了但没接线」，说明其风险模式是*半成品*而非*缺功能*。G1–G3 同属这一类。
4. **部分差距是刻意的**：安全边界上 pi-starter 在若干处已超越目标项目（见第三节），不应为了「对齐」而回退。

## 六、建议路线

```
第一步  G1–G4  骨架完整性          ~50 行，消除「声明≠生效」
第二步  G5–G6  文件 + SCM          编码刚需，区别于「能聊天」的能力
第三步  G7–G10 持久化/多密钥/MCP/计划模式   可运营性
─────────────────────────────────────────────
暂缓    插件系统 / DSH / 桌面端 / PTY / 定时任务
        （产品化需求，非脚手架刚需；PTY 在 Windows 上坑极深，
          目标项目用了 2330 行 + ConPTY 自愈才稳住）
```

每步完成后跑 `npm run verify`（typecheck + test + smoke + build）与 `npm run lint:unused`，
沿用现有门禁，不降低标准。
