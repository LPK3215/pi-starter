## 0. 一句话结论

**这是一个「工程纪律明显高于同类脚手架平均水准」的项目，但它当前最大的问题不是代码，而是「自我描述」与「自我认知」的失真。**

拆开说三句：

1. **作为壳子，它是我见过的最扎实的一类。** 门禁链条完整且真实（376 后端 + 11 前端 + 23 WS 冒烟 + 39 真进程 e2e + 8 嵌入验证，全绿），fail-closed 原则贯穿每一条 I/O 路径，注释写的是「为什么」而不是「做了什么」，很多条目附了真实踩坑记录。
2. **作为「通用智能体」，它目前是一个骨架完整但手脚偏少的个体。** 默认档我手里只有 7 个工具，**没有任何联网能力**，**没有跨会话记忆**。而 `rules.md` 第 1 条又要求我「凡是需要事实的地方必须调用工具核实、不要编造」——对外部世界的事实，我既无工具可核、又被规则禁止编造。这是「通用」这个定位下最实质的能力缺口。
3. **它 3 天写了 2.7 万行。** 59 个提交，从 `2026-10-08 00:31` 到 `2026-10-10`。这个速度本身是能力证明，也解释了为什么「文档一致性」和「注释与实现漂移」会成为主要缺陷——**代码跑在了文档前面，而且跑得很远**。

### 0.2 参考手册的生成器不只是文档，还是一个检查

`generate_reference.mjs` 在生成过程中带**硬断言**，任何一条不成立就非零退出：

- 从 `ClientMessage` union 解析出的命令集合，必须与 `protocol.ts` 里那个有编译期守卫
  （`Exclude<ClientMessage["type"], typeof CLIENT_MESSAGE_TYPES[number]> extends never`）的常量完全一致
  —— 等于拿编译期保证来校验这个解析器本身。
- `src/tools/*.ts` 里出现的每个工具名，必须在生成器的分组表里被登记；反之亦然。
  **新增一个工具却忘了归类，门禁直接红**，而不是让文档悄悄少一条。
- 代码里引用的 `PI_*` 必须都在 `.env.example` 里登记过。

写这个解析器时踩到一个真实的坑，记录在此：`rollback_conversation` 分支**内部**有一个单行 JSDoc
（`/** 走 SDK 官方 navigateTree ... */`），而按「找下一行 `*/`」的写法会把后面十几个分支全部吞掉 ——
表现是解析结果莫名少了 19 条命令。断言就是在这种情况下救的场：它不会静默生成一份缺条目的文档。

另外**刻意没做**的一件事：给 34 条协议命令强制要求 JSDoc。当前说明覆盖率是客户端 4/34、服务端 7/21，
手册如实把覆盖率印出来；但把它设成门禁只会逼出一批「为了过检查而补的空说明」，那比没有说明更糟。

### 0.3 关于覆盖率的两个坑（避免下一轮白干活）

1. **`ws.ts`（76%）与 `agent.ts`（66.5%）的数字是误导性的**，别照着它去补单元测试。它们的未覆盖段（`ws.ts` 的 191-263 / 275-304 / 307-342 等、`agent.ts` 的 112-343 即 `buildAgent()` 本体）**是被 `npm run smoke` 与 `npm run e2e` 覆盖的** —— 那两个套件跑在**独立进程**里，所以它们建立的覆盖率不会进入 `npm test` 的统计。真实覆盖率不低，只是「在这里看不见」。
   要在进程内覆盖它们，需要给 `buildAgent` 加一个会话工厂注入点、或引入 `--experimental-test-module-mocks` 去桩掉 SDK —— 都是**有设计代价的改动**，收益却不明确（已经有真进程 e2e 在验它们）。所以在没有明确缺陷驱动之前，不建议动。
2. **「覆盖率低」和「值得补测试」不是一回事。** 这一轮真正有价值的是 `file-routes.ts` 与 `current-time.ts` 这类：**代码在关键路径上、行为有分支、却从未被执行过**。而 `embeddings-transformers.ts`（53.77%）低是因为它需要一个可选依赖，`exec.ts`（78.97%）低是因为进程树操作难以在单测里稳定复现 —— 这两类补测试的性价比明显低得多。

### 0.4 第三轮：把「只测了假后端 / 只测了跨进程」的两处补成真实执行

第二轮之后剩下的两个可疑点是**测试真实度**问题，而不是覆盖率问题：

- `web.ts`（我新写的联网模块）**只测了假后端** —— `fetchPage` 里的字节上限、重定向、超时、content-type 判定**从未真实执行过**。补测时用本地 HTTP 服务跑真实抓取（注入 host 策略，否则回环地址会被自己的 SSRF 防护挡住），**当场看出两个 bug**：
  1. `readCapped` 写的是 `total + value.length >= maxBytes`，于是正文**恰好等于**上限时误报「已截断」——一个字都没丢却对模型说截断了。
  2. **重定向在 `fetch` 跟完之后才校验**：`redirect: "follow"` 意味着 `302` 到内网时请求**已经发出去了**，事后检查只能阻止「读回内容」，挡不住「内网端点被触发」。已改为 `manual` 自己跟、**每跳发请求前校验**、共用超时、`MAX_REDIRECTS` 封顶；回归用例断言「被禁主机收到 0 个请求」。
- `ws.ts` 的低覆盖率不是没测，而是**只被跨进程的 smoke 覆盖**。补了进程内分派层测试后，确认错误翻译是对的（顶层 catch → `clientErrorMessage`），并锁住「一连串畸形输入之后 `ping` 仍必须得到 `pong`」。

结论仍与 §0.3 一致，但更具体：**「测过」要问是哪种测法** —— 假后端测不出真实字节/重定向行为，跨进程测不进程内统计。问「这段代码有没有被真实执行过」，比问「覆盖率多少」有效得多。

覆盖率 91.43% → **92.26%**（443 用例，棘轮抬到 lines 92 / branches 79 / functions 84）。

### 0.5 工具层的坑：`--experimental-test-coverage` 的「未覆盖行号」不可信

`node --test` 是多进程的，覆盖率按进程采集后汇总。实测发现**百分比大致可信，但「uncovered lines」那一列不可信**：同一份 `routes.ts`，只跑 `app.test.ts` 时报 `142-152` 未覆盖，全量跑时报 `143 146-151` —— 两次的列表互相都不是对方的子集，而那些行明明都被执行过（对应用例是通过的）。

**所以选目标时只看文件级百分比，把行号列表当提示而不是依据。** 这条与 §0.3 是同一个教训的两面：覆盖率的**数字**和**位置**都会骗人，唯一可靠的判据是「这段代码有没有被真实执行过、断言够不够硬」。

顺带一个正面结论：`docs/check` + 覆盖率棘轮这套门禁本身是有效的（数字一变就红），问题只在于**解读**它。

## 1. 审查立场：什么叫「站在智能体的角度」

我按两层来评：

- **第一层：我在这里当智能体是什么体验。** 我的身份从哪来、手里有什么、被什么挡住、能记住什么、出错会怎样、能不能看见自己。这一层决定「这个壳子作为通用智能体是否成立」。
- **第二层：造这个壳子的工程本身做得怎么样。** 架构、安全、性能、可维护性、测试、文档、交付。

两层结论会放在一起，因为它们互相印证：**壳子造得很硬，个体体感却很薄**——这不是矛盾，是「脚手架」这个定位的自然结果，但需要被明确指出来。

## 2. 我在这里的自画像（第一层）

### 2.1 我的身份从哪来

| 项 | 事实 |
|---|---|
| 人格 | [`src/prompts/persona.md`](../src/prompts/persona.md)，703 字节 |
| 工作约束 | [`src/prompts/rules.md`](../src/prompts/rules.md)，1,561 字节，9 条 |
| 系统提示词组装 | `src/prompts/composer.ts`（4,267 字节） |
| 隔离策略 | `noExtensions: true` / `noSkills: true` / `noPromptTemplates: true` / `noContextFiles: !includeAgentsFiles` |

`persona.md` 给我的定义是：「你是 **Pi Starter**，一个基于 pi-agent SDK 构建的通用智能助手」。回答风格要求「结论先行、简洁结构化、用中文」。

**评价：身份定义是「最小可用」的。** 它没有领域知识、没有语气样例、没有价值观/拒答边界（拒答边界只靠 `rules.md` 第 4 条「安全边界」一条兜着），也没有「我是谁、我不做什么」的负面清单。作为脚手架这是**正确的取舍**（业务要覆盖的就是这段），但作为「你就是这个产品」的默认体验，它读起来像占位符而不是人格。

`rules.md` 反而写得很好：9 条全是**可执行的动作约束**，不是空话。「不编造数据」「单步原则」「工具失败先读错误再重试一次」「exec 不是交互式终端」「相对路径相对技能目录解析」——这些是我真正能照着做的规则。**这是这个项目里我最欣赏的一小段文本。**

### 2.2 我默认手上有什么

默认档 `PI_BUILTIN_TOOLS=off`，`sessionToolPolicy("off")` 返回 `{ tools: ["read", ...extra] }`（`src/config.ts:602-615`）。合并后的默认工具面：

| 工具 | 来源 | 能力 |
|---|---|---|
| `read` | SDK 白名单（off 档唯一内置） | 读文件；**技能正文必须靠它加载**（`<available_skills>` 只给目录） |
| `current_time` | `src/tools/current-time.ts` | 取当前时间 |
| `ask_user_question` | `src/tools/ask-user-question.ts` | 向人反问（HITL，前端已接弹窗） |
| `search_knowledge` / `read_knowledge` | `src/tools/knowledge.ts` | 检索/读取 `src/knowledge/*.md` |
| `db_status` / `db_query` | `src/tools/database.ts` | 连通性 / 只读 SELECT |

**要点：**

- **没有 `bash` / `edit` / `write`**（要 `PI_BUILTIN_TOOLS=coding` 显式打开）。这个默认是对的：README 的理由很实在——「我们**总是**传 `tools`，它就成了 SDK 的硬白名单；不传才是开启全套」。所以必须显式打开，而不是靠「没传」意外获得。
- **没有 `exec` / `exec_jobs` / `exec_stop`**（同样只在 coding 档）。
- **完全没有联网工具。** 全仓库 `src/tools/` 里没有任何 `fetch` / HTTP 客户端类工具，MCP 桥虽然存在但默认不接任何 server。

**这是「通用智能体」定位下最实质的缺口。** 我能读本地文件、查本地知识库、查本地 SQLite、问人、看时间——但**我看不见互联网**。当我被问到「这个库最新版是多少」「这个 API 现在怎么用」「今天发生了什么」时，我的正确行为是 `rules.md` 第 1 条：承认无法核实。这个行为是对的，但它意味着**我在通用场景下的可用半径被压得很窄**。

### 2.3 我被允许做什么 / 被什么挡住

四层拦截叠加，顺序即优先级（`src/extensions/index.ts` + `src/approval/` + `src/modes/plan-mode.ts`）：

```
SDK tool_call
 ├─ guard 扩展     ：危险命令正则（extensions/shell-rules.ts 单一事实源）
 │                   + realpath 路径双重校验（guard.ts:94-103）
 │                   + 敏感文件名拦截（secret-files.ts）
 │                   + exec 的 cwd 越界
 ├─ plan-mode 扩展 ：写类工具 → 硬 { block }
 ├─ approval 扩展  ：deny（不可被策略覆盖）/ ask（问人，超时判拒）/ allow
 └─ 执行 → tool_result → audit 扩展（耗时日志）
```

还有一层**非拦截的资源闸门**：`ToolWatchdog`（工具超时默认 20 分钟 → abort）。

**值得单独表扬的设计：**

- **`deny` 不可被策略覆盖**（`src/approval/policy.ts`）。这是真正的安全属性，不是「照抄参考实现」。很多同类项目的审批是「策略可覆盖一切」，那样 `deny` 就退化成了默认值。
- **审批超时判拒而不是判允**（fail-closed 的正确方向）。
- **危险命令表已从两份漂移的正则合并为单一事实源**（`src/extensions/shell-rules.ts`，guard 与 approval 共用）。
- **realpath 校验已补齐**：`guard.ts` 现在会解析符号链接（`realpathOfNearestExisting`），与 `FileService` 同强度——**旧报告里「三层保护强度不一致」这条已经不成立**。

**但当前仍有三个真实缺口（已核实，非旧报告残留）：**

1. **`bash` 命令体本身没有路径约束。** `src/extensions/guard.ts:128` 命中正则后 `if (isToolCallEventType("bash", event)) return undefined;` 直接放行——命令里 `cd /`、`cat /etc/passwd`、`curl` 外网都不经过 `isPathInsideCwd`。项目**自己声明过这不是沙箱**（README 与 SECURITY.md 都写了），所以这是「已声明的取舍」而非隐瞒；但 README 的 "Hardened by default" 措辞容易让人高估强度。
2. **审批默认关闭**（`src/settings.ts:265-266`：`toolApprovalEnabled: false` + `approvalMode: "off"`）。叠加 `off` 档内置工具默认关闭，整体风险可控；但要说清楚：**默认态下真正生效的只有 guard 的正则与 `deny` 类规则**，`rm -rf` 这类 `ask` 规则是静默放行的（靠 guard 正则兜住）。
3. **Unix `exec` 主路径仍继承 `process.env`**（`src/exec/runner.ts:432-434`），而 `src/child-env.ts` 的「剔除 `PI_API_KEY*`」只接进了 MCP（`mcp/client.ts:80`）与 Windows 分支（`runner.ts:426`）。**且 `runner.ts:474` 的注释声称「凡 spawn 的地方口径一致，避免漏一个」，恰好漏的就是 Linux/macOS 主路径。** 这是本轮评估里最值得优先级最高的一条——它同时是安全问题、也是文档一致性问题。

### 2.4 我的记忆边界

| 类型 | 是否持久 | 证据 |
|---|---|---|
| 会话历史（消息、工具往返） | **是**（`inMemory: false` + `sessionDir` + `SessionCatalog`；重启后 `open_conversation` 可接回） | `src/sessions/store.ts`、`src/agent.ts:650-670` |
| 会话树编辑（改名/回退/编辑/分叉/真删除） | **是** | `src/sessions/edit.ts` |
| 条目标签（书签） | **是**（`SessionManager.appendLabelChange`） | `src/session-hub.ts` `labels()` / `setLabel` |
| 运行时设置（template / disabledTools / thinkingLevel / approval） | **否**，默认 `memorySettingsPort()`，重启重置 | `src/settings.ts:313`；README 亦声明 |
| 跨会话长期记忆 / 用户画像 | **不存在** | 全仓库无此机制 |

**这是第二大能力缺口：我没有「上一次」的概念。** 会话历史可以把**同一段对话**接回来（而且做得很好，e2e 里专门验证了工具调用配对不悬空），但**新开一段对话我就是从零开始的陌生人**。对通用助手来说，「记住用户偏好、记住上次结论」是体验的核心部分，这里完全没有。

### 2.5 我出错时会发生什么

这一层做得比大多数项目细：

- **错误分层**：`AppError.safeToExpose` 默认 `false`；`internal` 的真实文案只进服务端日志，客户端拿通用文案。
- **SSE 内的错误翻译**：`/chat` 状态码已提交后不能改状态码，项目**在 SSE 帧内复用同一套暴露规则**翻译错误——这个坑踩得很清楚（README 与代码注释都记录了）。
- **自动重试可见**：SDK 的 `auto_retry_start` / `auto_retry_end` 被翻译成 notice 帧，我重试时用户看得见「第 N 次恢复 / 最终失败」，而不是静默卡住。
- **工具超时**：watchdog 到点 abort 本轮并推 notice。
- **优雅停机**：`src/graceful.ts` 的兜底定时器**先建后跑步骤**（注释记录了原实现「进程永久挂死」的真 bug）。
- **原子写 + 损坏回落**：settings / approval rules / provider-keys / session index / plan-mode 五处统一（tmp + rename + 失败告警但不回滚内存）。

### 2.6 我能不能看见自己

能，而且看得比大多数项目清楚：

- **结构化日志 + 自动值级脱敏**（`src/log.ts`）：递归深度受限、Error 特殊处理（否则 spread 会丢 `message`）。
- **14 个运行时指标**，JSON 与 Prometheus 双格式（`/metrics`）。
- **liveness / readiness 分离**（`/health` 不碰依赖，`/health/ready` 503 报依赖故障）——这个区分让编排器不会「模型挂了就重启进程」，是成熟做法。
- **日志查询/分页 REST**（`src/http/log-routes.ts`，443 行，含字节偏移无损分页）。
- **AI 运行观测**：`logRunSummary()` 记录 model / stopReason / tokens / cost / contextUsage，且读数来自与快照同一个 estimator，保证「日志不会和客户端看到的不一致」。

## 3. 做得好的地方（第二层，按证据分 5 组）

### 3.1 架构与抽象

1. **协议单源 + 编译期完备性断言。** `src/protocol.ts` 是唯一协议源，新增命令漏登记会**编译失败**（`satisfies` + `Exclude extends never` 手法）。前端直接把 `src/protocol.ts` 映射成 `@pi/protocol`（`web/vite.config.ts:16-17`），两侧类型不可能漂移。这是全项目最干净的一处设计。
2. **双通道行为已收敛为共享函数。** `src/capabilities.ts`（REST `/capabilities` 与 WS `capabilities` 帧共用）与 `src/models.ts` 的 `toUiModel`——**旧报告「REST 与 WS 各写一份整形」已不成立**。更进一步，`agent.ts` 的 `resourceLoaderOptions()` 被 REST/WS 与官方 RPC 三条装配路径共用（`agent.ts:558-609`），从签名上消除「三条路径在隔离/人设/工具上分叉」。
3. **SDK 私有形状收敛到 `src/sdk-adapter.ts`。** 原先把 `session.compact` / `session.agent.state.messages` / `session.sessionManager` 等私有访问散在各处、每处各写一遍 `typeof` 兜底；现在收敛为 7 个带存在性检查的访问器（`sdk-adapter.ts:37-95`）。**残留 1 处**：`session-hub.ts:1190-1197` 的 `navigateTree` 仍就地断言。
4. **`resolveToolList()` 刻意在 `createSession` 内部求值**（`agent.ts:546-550`）。因为 SDK 的 `tools` 是构造后不可改的硬白名单，运行期新增的 MCP 工具只能「下次建会话生效」——这个反直觉的取舍被正确实现并注释。
5. **前端适配层设计扎实**（`web/src/pi/`，自研核心约 2.7k 行）：跨会话帧过滤（后端把每条已打开对话的帧都推到同一 socket，前端必须按 `conversationId` 过滤）、修订链断链自愈（`rev`/`baseRev` 不连续即请求全量快照）、指数退避重连（句柄可取消）、快照到达时以快照为准回填流式文本。这些都有回归测试。

### 3.2 安全与 fail-closed

6. **密钥纪律是教科书式的。** `provider-keys.ts` 的 `describe()` **在类型层面就不可能返回 `apiKey`**；落盘 0600；临时文件也 chmod。这堵住了「调试接口顺手把 key 吐出去」这一整类事故。
7. **路径校验双重且 fail-closed。** `assertSessionFileAllowed`（绝对路径 + `.jsonl` + realpath 在允许根内，**根 realpath 失败就丢弃这个根**而不是退回字面路径）在 `newConversation` 与 `resolveSessionManager` 各查一次——不依赖调用方注释。
8. **敏感文件名黑名单已补齐且有单源。** `src/secret-files.ts` 的 `DEFAULT_DENY_NAMES`（`.env` / `.env.*` / `*.pem` / `*.key` / `id_rsa` / `credentials*` / `auth.json`）同时支撑 `FileService.denyNames` 与 `guard`，连**符号链接的真实目标名**也拦（`files/service.ts:146-158`）。**旧报告 P1-1 的主体已修复。**
9. **`deny` 不可被策略覆盖**（`approval/policy.ts`）。
10. **子进程环境已做白名单裁剪**（`src/child-env.ts`）——MCP 与 Windows 路径已接入，Unix `exec` 主路径未接入（见 §2.3 第 3 条，这是残留）。
11. **不扫描本机 `~/.pi` 的扩展/技能/提示词模板**（`noExtensions` / `noSkills` / `noPromptTemplates`），避免「别人的机器配置污染这个垂类 agent」。这是很清醒的一条：本地 pi 扩展可以重新注册 `bash`。

### 3.3 资源与韧性

12. **封顶成体系且每一处都「报截断而不是静默失败」**：`MAX_SNAPSHOT_MESSAGES=500` / `MAX_INDEX_ENTRIES=500` / 每查询 200 行 / 每个知识文档 512KB / `MAX_JOBS` / `MAX_FINISHED` / `MAX_OUTPUT_BYTES` / `MAX_COMMAND_CHARS` / `MAX_USER_RULES` / `MAX_MCP_SERVERS` / 并发子代理 3 + 队列上限 32（`subagents/index.ts:48`）。

## 6. 关于「我没有个人业务」——正面回答

**我不认为这是错的，而且我认为你的论证比多数人以为的更站得住。** 三条理由：

**理由一：通用性本身就是产品属性，不是「还没想好做什么」。**
这个项目的价值主张写得很清楚：**「垂直 Agent 的起跑线」**。判据不是「它自己会不会卖货」，而是**「把它接到一个业务上要多久」**。项目自己给出了这个判据的验证方式——`scripts/verify-embed.mjs` 8 项断言，覆盖 `createApp()` 返回值契约、内核路由、以及**三种鉴权挂法的实测结论**。这不是口号，是可执行的事实。

**理由二：它已经在做「没有业务也能活」的实事。**
默认档能读文件、查知识库、查 SQLite、问人、看时间；能重启后接回历史对话（且验证了工具调用不悬空）；能多对话并发（cap 8 + LRU）；能编辑/回退/分叉会话树；能改标签做书签。**这些都不是「某个业务的功能」，而是「任何业务都会需要的底座」。** 把它们做扎实，本身就是交付。

**理由三：真正的风险不在「没有业务」，而在「通用与可用之间的缝」。**
我在 §4 P7 列的那六条缺口里，**P7-1（无联网）与 P7-2（无记忆）是两条会被人拿来质疑「通用」这个词的**。不是因为它们让项目变差，而是因为：
- `rules.md` 明确要求「不编造数据、必须工具核实」——**这个要求把联网从「加分项」变成了「能力闭环的必需品」**。没有它，我的正确行为只能是频繁说「我无法核实」，这与「通用智能助手」的默认预期有落差。
- 没有跨会话记忆，「通用」就只是「无状态」的另一种说法。

**所以我的判断是：定位没问题，方向没问题，缺的是「让通用这个词兑现」的最后两块砖。** 补上联网与记忆，这个项目从「优秀的脚手架」变成「优秀的通用智能体」的门槛就跨过去了。

## 7. 本轮（2026-10-10）已完成的性能修复记录

作为附注，本轮审查期间对快照热路径（`buildState`）做了三处修复，均已实测通过：

| # | 修改 | 效果 |
|---|---|---|
| 1 | `contextIndex()`：一趟 `buildContextEntries()` 同时取「消息→条目 id」与「官方标签」 | 每周期由 2 遍会话树遍历 → 1 遍（SDK 的 `buildContextEntries()` 每次都先 `getEntries()` 全量过滤，并不便宜） |
| 2 | `overBudget` 用同一个 `totalTokens` 短路 + 复用 `contextTokens` | 去掉每周期一次全量 token 累加，以及一份马上被丢弃的 trim 计划数组 |
| 3 | `listConversations()` 的休眠段按「索引数组引用 + 在册 id」缓存 | 每周期少分配约 500 个对象；索引 upsert/remove 换新数组即自然失效，无需失效钩子 |

净效果：`buildState` 由「1 遍投影 + 2 遍树遍历 + 2 次 token 全量累加」降为「1 遍投影 + 1 遍树遍历 + 1 次 token 累加」。残留见 §4 P2。
